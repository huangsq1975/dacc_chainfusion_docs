估算前提

  • 人天指熟悉這幾個 repo（NestJS、TypeORM、Next.js 12、Apollo）的工程師一天的有效開發量，包含該功能的單元測試和自測。
  • 團隊配置：後端 2 人、admin 前端 1 人、APP 前端 1 人。後端是關鍵路徑：後端 96 人天 ÷ 2 人 ≈ 9.6 週；admin 6.3 週、APP 6.7 週，前端可以在後端 API 定型後並行。日曆時間再加 20% 的協調與相依等待。
  • 先用 mock server：M1 到 M10 在 mock server 上開發，不必等 Aegis dev 環境；M12 的端到端驗證需要 Aegis dev 環境。
  • 區間：下限是 −15%，上限是 +25%。上限反映冷錢包 API 仍是草稿、欄位可能調整，以及 Aegis 人工審核造成的等待。
  • 不含：UI 視覺設計、業務與法務確認、Aegis 側的開發與審核時間、正式環境的資安審查。

建議排期

依改動說明第 11 節的順序，按 4 人團隊排：

  1. 第 1–3 週：M0 前置修正、M1 冷錢包基礎元件與 mock server（後端）；前端同時做 M2 註冊頁與 M4 的 APP 提交 bond 表單。
  2. 第 3–6 週：M2 註冊後端、M3 公司 KYC 改寫與開戶、M4 bond 資料與審核流程、M5 建立 CMTAT 合約；admin 做 KYC 頁與 CMTAT 發行面板。
  3. 第 6–9 週：M6 認購、M7 分配、M8 交割與逾期註銷，這是首發的主線，前後端同步進行。
  4. 第 9–10 週：M9 登記冊與對帳、M10 存續與到期、M11 通知與權限。
  5. 第 10–12 週：M12 對 Aegis dev 環境端到端驗證、回歸測試、修正與上線。這段的長短取決於 Aegis dev 環境何時可用，以及審核 SLA；保守估計會延到第 15 週。
如果 USDSN27 要先上線，可以把 M10 的轉讓與條款變更延後，首發只到 ISSUED 加上到期贖回，約可省下 1–1.5 週。

影響工時的風險與未定事項

  • 冷錢包 API 仍是草稿（指南 v0.7）：欄位調整會影響 M1、M3、M5、M8。mock server 要跟著指南版本更新。
  • Aegis dev 環境與審核 SLA 未定：M12 的長度、交割日和付款期限的設定都依賴它。
  • 付息與贖回金額由誰計算未定：目前 M10 只估「記錄與顯示」。如果由 DigiQuick 計算，要另加約 5–8 人天（結構化付息日、計息基礎、計算與覆核）。
  • 機構投資人資格門檻未定：影響 M3 審核頁要收的證明，審核頁先做成通用的，工時影響小。
  • 同一家公司能否兼任發行方與投資人：目前按「只選一種身份」估。如果要兼任，M2、M3 約加 3–4 人天。
  • 發行方關係人能否認購自己的 bond：只是 M7 多一項檢查，約 1 人天。
  • 既有程式沒有測試：M0 修 jest 只估基本可用；回歸測試其他 8 種資產的工作算在 M12 的緩衝裡。
